# Trip Service

Сервис поездок для лабораторных работ 1 и 2. Создаёт поездку, отдаёт её по id, завершает. Данные лежат в PostgreSQL.

## Запуск

Поднять окружение:

```
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

После этого появится файл `.env` с адресами PostgreSQL и коллектора OpenTelemetry. Команда `tripgoctl connect` покажет ссылки на Jaeger, Grafana и Prometheus.

Накатить миграции:

```
make migrate
```

Запустить сервис:

```
make run
```

Сервис слушает адрес из `HTTP_ADDR`. В `.env.example` задан `:8080`.

## Переменные окружения

Полный список с примерами значений в `.env.example`. Короткое описание:

- HTTP_ADDR: адрес, на котором слушает сервер
- LOG_LEVEL: уровень логирования
- SHUTDOWN_TIMEOUT: сколько ждём при остановке, прежде чем выйти принудительно
- DATABASE_URL: адрес PostgreSQL
- DATABASE_MAX_CONNS, DATABASE_MIN_CONNS: размер пула соединений
- DATABASE_MAX_CONN_LIFETIME: сколько живёт одно соединение
- DATABASE_CONNECT_TIMEOUT: таймаут создания соединения с базой
- DATABASE_QUERY_TIMEOUT: таймаут SQL-запроса и всего блока транзакции
- HTTP_READ_TIMEOUT, HTTP_READ_HEADER_TIMEOUT, HTTP_WRITE_TIMEOUT, HTTP_IDLE_TIMEOUT: таймауты HTTP-сервера, необязательные, по умолчанию 10s, 5s, 10s и 60s

Для телеметрии обязателен OTEL_EXPORTER_OTLP_ENDPOINT с адресом коллектора. Остальные настройки OpenTelemetry есть в `.env.example`.

Если не задана любая из обязательных переменных, сервис не запустится и напишет в лог, какой переменной не хватает. Свои значения для HTTP_*_TIMEOUT можно задать в таблице `[env]` файла `environment.toml`: `tripgoctl environment start` допишет их в `.env`.

## Ручки

POST /api/v1/trips: создать поездку. Тело: user_id, driver_id, start_point, end_point, price. В ответ 201 и созданная поездка. Если у водителя уже есть активная поездка, то 409 driver_busy.

GET /api/v1/trips/{tripId}: получить поездку по id. 404, если такой поездки нет.

POST /api/v1/trips/{tripId}/finish: завершить поездку. 200 и обновлённая поездка. 409 trip_completed, если поездка уже завершена. 404, если поездки нет.

GET /health: проверка, что процесс жив. В базу не ходит.

GET /ready: проверка, что база доступна. 503, если PostgreSQL недоступен.

Ошибки возвращаются в формате application/problem+json (RFC 9457), с полем code для машинного разбора: driver_busy, trip_not_found, trip_completed, invalid_request, internal_error. Неизвестный путь даёт 404 not_found, неверный метод 405 method_not_allowed.

## Архитектура

Правила поездки находятся в `internal/domain/trip`, сценарии создания, получения и завершения в `internal/usecase/trip`. HTTP вызывает эти сценарии через интерфейсы. Сценарии используют домен и получают репозиторий и менеджер транзакций через интерфейсы. Домен не зависит от HTTP и базы. Зависимости собираются в `internal/container`, который вызывается из main. Правила импортов проверяет depguard.

Интерфейсы объявлены в `contract.go` рядом с кодом, который их использует. Каждый пакет описывает только нужные ему методы. При добавлении gRPC домен и сценарии останутся прежними.

SQL находится в `internal/repository/trip`, подключение к базе и телеметрия в `internal/infra`. Пакет запуска сохранил имя `cmd/trip-service` из первой лабы. Пакет `internal/http` называется httpserver, чтобы не пересекаться с net/http. Общий конвертер ответа в `internal/http/trip/dto` заменяет отдельные convert.go у получения и завершения поездки. В `internal/model` остались входные данные сценариев и запись идемпотентности, сама поездка перенесена в домен.

## Телеметрия

Логи пишутся в stdout в формате JSON. Поля trace_id и span_id связывают запись с трейсом. OpenTelemetry отправляет HTTP и SQL спаны и метрики по OTLP. В http.route используется шаблон маршрута. Ошибки экспорта пишутся в лог, сервис продолжает обрабатывать запросы.

Сохранены [трейс Jaeger](docs/observability/jaeger-trace.png), [метрики Grafana](docs/observability/grafana-metrics.png) и [запись лога](docs/observability/request.log).

## Решения

Уровень изоляции транзакций: Read Committed, дефолт PostgreSQL. Он определяет, какие конкурентные изменения видит запрос: только уже закоммиченные, и каждый запрос заново. На этом держится завершение поездки: второй UPDATE ждёт коммита первого и перепроверяет условие status='active', строка уже не подходит, и обновление не происходит. На Repeatable Read тот же конфликт закончился бы ошибкой сериализации, которую пришлось бы обрабатывать повтором. Запрет двух активных поездок у одного водителя обеспечивает partial unique index `trips_one_active_per_driver_idx` (уникальный driver_id среди активных поездок): базе достаточно проверить индекс при вставке строки, уровень изоляции здесь ничего не меняет. Атомарность создания (запись в trips и запись в trip_status_history сохраняются вместе или не сохраняются вовсе) даёт сама транзакция: commit или rollback, независимо от уровня изоляции.

Менеджер транзакций (`internal/infra/postgres/transaction`) это один метод Do(ctx, fn). Do открывает транзакцию, кладёт её в context.Context и вызывает fn с этим контекстом. Если fn вернула ошибку, происходит откат. Если fn отработала без ошибки, происходит commit. Если внутри fn паника, происходит откат, а сама паника пробрасывается дальше, не гасится. Репозиторий сам не решает, использовать транзакцию или нет: он берёт исполнителя запроса из контекста (функция ExecutorFromContext). Если транзакция там есть, работает через неё, если нет, работает через обычный пул соединений. Из-за этого репозиторий вообще не знает про pgx.Tx и может одинаково работать и внутри Do, и вне его. Вложенный вызов Do внутри другого Do не открывает вторую транзакцию: он видит, что транзакция уже есть в контексте, и просто вызывает fn напрямую.

Завершение поездки защищено условием `WHERE id=$1 AND status='active'` в UPDATE. Если два запроса прочитали активную поездку одновременно, обновить её сможет только один. Он получит 200, второй получит 409 trip_completed. Запись в истории создаётся в той же транзакции. Если поездки нет, ответ будет 404.

Тело POST /api/v1/trips проверяет валидатор запросов по самому контракту `openapi.yaml` (nethttp-middleware на kin-openapi). Обязательные поля, null, диапазоны координат, price не меньше нуля, типы значений и запрет лишних полей берутся из схемы. Домен дополнительно проверяет входные данные в trip.New. Спека встроена в сгенерированный `internal/generated/api.gen.go`, поэтому после изменения контракта достаточно `make generate`. Нулевые user_id и driver_id также отклоняются. Ошибки валидатора отдаются как 400 invalid_request.

Остановка. SHUTDOWN_TIMEOUT задаёт общий бюджет на всё: сначала http.Server.Shutdown ждёт запросы в полёте, затем сбрасывается телеметрия и закрывается пул соединений. Если запросы не завершились за бюджет, сервис пишет в лог, что бюджет исчерпан, и выходит с кодом 1 без ожидания. Незавершённые транзакции откатывает PostgreSQL при обрыве соединения. Штатная остановка заканчивается кодом 0.

## Идемпотентность (задание со звёздочкой)

POST /api/v1/trips с заголовком Idempotency-Key и uuid в значении работает так:

- новый ключ: создаёт поездку, 201
- тот же ключ и то же тело: 200 и та же поездка, вторая не создаётся
- тот же ключ и другое тело: 409 idempotency_conflict
- без заголовка: обычное поведение, как описано выше

Ключ живёт 24 часа, как у Stripe. Храним его в таблице idempotency_keys (миграция 00003). Протухшие строки не удаляются: при чтении они не находятся (условие по created_at), а при повторном использовании ключа резервирующий INSERT перезаписывает такую строку через ON CONFLICT DO UPDATE с тем же условием, поэтому протухший ключ создаёт новую поездку. Активной фоновой очистки нет, потому что воркер-пул, на котором такая очистка обычно строится, появляется только в лабораторной работе 3.

Ключ атомарно резервируется через INSERT с ON CONFLICT (key) DO UPDATE по условию протухшей строки: у живого ключа затронутых строк нет, и запрос понимает, что ключ занят. Резервирование происходит до создания самой поездки. Внешний ключ idempotency_keys.trip_id к trips.id объявлен DEFERRABLE INITIALLY DEFERRED, поэтому можно вставить резервирующую строку с trip_id, которого в trips пока ещё нет: проверка внешнего ключа откладывается до COMMIT той же транзакции, а к этому моменту строка в trips уже вставлена.

Порядок операций важен. Если бы поездка создавалась раньше резервирования ключа, несколько параллельных запросов с одним ключом на одного водителя сначала столкнулись бы друг с другом на ограничении "один активный водитель у trips", а не корректно дедуплицировались бы по ключу. Это была реальная ошибка, которую поймал на тесте: 10 параллельных запросов с одним новым ключом сначала дали один 201 и девять 409 driver_busy вместо одного 201 и девяти 200. После того как поменял порядок операций (сначала резервирование ключа, потом создание поездки), тот же тест даёт один 201 и девять 200 с одним и тем же id у всех.

## Dockerfile (задание со звёздочкой)

Сборка многостадийная. Первая стадия на образе golang:1.27-alpine компилирует статический бинарь с CGO_ENABLED=0. Вторая стадия на образе gcr.io/distroless/static-debian12:nonroot содержит только этот бинарь, без shell и без toolchain. Процесс идёт от uid 65532, не от root, это дефолтное поведение выбранного базового образа.

Собрать образ:

```
docker build -f deploy/Dockerfile -t trip-service .
```

Размер итогового образа: 41.5 MB.

Запустить рядом с PostgreSQL и коллектором в одной docker-сети (переменные такие же, как в .env.example, адреса указывают на контейнеры по их именам в сети):

```
docker run -d --network <сеть> -p 8080:8080 \
  -e HTTP_ADDR=:8080 -e LOG_LEVEL=info -e SHUTDOWN_TIMEOUT=10s \
  -e DATABASE_URL=postgres://tripgo:tripgo@<контейнер-бд>:5432/tripgo?sslmode=disable \
  -e DATABASE_MAX_CONNS=10 -e DATABASE_MIN_CONNS=2 \
  -e DATABASE_MAX_CONN_LIFETIME=30m -e DATABASE_CONNECT_TIMEOUT=5s -e DATABASE_QUERY_TIMEOUT=3s \
  -e OTEL_EXPORTER_OTLP_ENDPOINT=http://<контейнер-коллектора>:4318 \
  trip-service
```

/ready отвечает 200, когда база доступна. docker stop отправляет SIGTERM, сервис укладывается в SHUTDOWN_TIMEOUT: пишет в лог "shutdown signal received", потом "trip-service stopped" и выходит сам, до принудительного SIGKILL дело не доходит

## Проверки

`make test` запускает тесты с проверкой гонок и показывает покрытие домена и сценариев. `make lint` запускает golangci-lint, `make fmt` форматирует код. Нужен golangci-lint 2.14.0.

`make test-integration` проверяет репозиторий на PostgreSQL. Перед запуском нужны `.env`, поднятое окружение и применённые миграции.

`make generate` обновляет код по OpenAPI и моки. `make mutation` запускает мутационные тесты, для него нужен gremlins 0.6.0. Результаты описаны в [отчёте](docs/mutation-testing.md).
