# Trip Service

Сервис поездок для лабораторной работы 1. Создаёт поездку, отдаёт её по id, завершает. Данные лежат в PostgreSQL.

## Запуск

Поднять окружение:

```
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

После этого появится файл `.env` с адресом PostgreSQL.

Накатить миграции:

```
make migrate
```

Запустить сервис:

```
make run
```

Сервис слушает адрес из `HTTP_ADDR` (по умолчанию `:8080`).

## Переменные окружения

Полный список с примерами значений в `.env.example`. Короткое описание:

- HTTP_ADDR: адрес, на котором слушает сервер
- LOG_LEVEL: уровень логирования
- SHUTDOWN_TIMEOUT: сколько ждём при остановке, прежде чем выйти принудительно
- DATABASE_URL: адрес PostgreSQL
- DATABASE_MAX_CONNS, DATABASE_MIN_CONNS: размер пула соединений
- DATABASE_MAX_CONN_LIFETIME: сколько живёт одно соединение
- DATABASE_CONNECT_TIMEOUT: таймаут подключения к базе на старте
- DATABASE_QUERY_TIMEOUT: таймаут одного SQL-запроса

Если какая-то из этих переменных не задана, сервис не запустится и напишет в лог, какой переменной не хватает.

## Ручки

POST /api/v1/trips: создать поездку. Тело: user_id, driver_id, start_point, end_point, price. В ответ 201 и созданная поездка. Если у водителя уже есть активная поездка, то 409 driver_busy.

GET /api/v1/trips/{tripId}: получить поездку по id. 404, если такой поездки нет.

POST /api/v1/trips/{tripId}/finish: завершить поездку. 200 и обновлённая поездка. 409 trip_completed, если поездка уже завершена. 404, если поездки нет.

GET /health: проверка, что процесс жив. В базу не ходит.

GET /ready: проверка, что база доступна. 503, если PostgreSQL недоступен.

Ошибки возвращаются в формате application/problem+json (RFC 9457), с полем code для машинного разбора: driver_busy, trip_not_found, trip_completed, invalid_request, internal_error.

## Решения

Уровень изоляции транзакций: Read Committed, это дефолт PostgreSQL. Поднимать выше смысла не было, потому что запрет "у одного водителя не может быть двух активных поездок" держит не изоляция транзакции, а partial unique index в базе (`trips_one_active_per_driver_idx`, уникальный по driver_id только среди активных поездок). Это работает при любом уровне изоляции, потому что уникальность индекса проверяет сама база при вставке строки, а не транзакционный снапшот. Изоляция здесь нужна только для одного: чтобы вставка в trips и вставка в trip_status_history при создании поездки прошли либо обе, либо ни одна.

Менеджер транзакций (`internal/txmanager`) это один метод Do(ctx, fn). Do открывает транзакцию, кладёт её в context.Context и вызывает fn с этим контекстом. Если fn вернула ошибку, происходит откат. Если fn отработала без ошибки, происходит commit. Если внутри fn паника, происходит откат, а сама паника пробрасывается дальше, не гасится. Репозиторий сам не решает, использовать транзакцию или нет: он берёт исполнителя запроса из контекста (функция ExecutorFromContext). Если транзакция там есть, работает через неё, если нет, работает через обычный пул соединений. Из-за этого репозиторий вообще не знает про pgx.Tx и может одинаково работать и внутри Do, и вне его. Вложенный вызов Do внутри другого Do не открывает вторую транзакцию: он видит, что транзакция уже есть в контексте, и просто вызывает fn напрямую.

Завершение поездки защищено от гонки условием прямо в UPDATE: `UPDATE trips SET status='completed', finished_at=... WHERE id=$1 AND status='active'`. Если два запроса на finish придут одновременно, у базы нет момента, когда оба увидят статус active и оба его поменяют, потому что обновление и проверка статуса это одна операция. Тот запрос, который применился, получает RowsAffected=1 и 200. Второй получает RowsAffected=0, и код дополнительно смотрит, существует ли поездка вообще: если существует, значит уже завершена (409 trip_completed), если не существует, значит её вообще нет (404).

## Идемпотентность (задание со звёздочкой)

POST /api/v1/trips с заголовком Idempotency-Key и uuid в значении работает так:

- новый ключ: создаёт поездку, 201
- тот же ключ и то же тело: 200 и та же поездка, вторая не создаётся
- тот же ключ и другое тело: 409 idempotency_conflict
- без заголовка: обычное поведение, как описано выше

Ключ живёт 24 часа, как у Stripe. Храним его в таблице idempotency_keys (миграция 00003). Протухшие строки просто не находятся при чтении, потому что в запросе есть условие по created_at. Активной фоновой очистки нет, потому что воркер-пул, на котором такая очистка обычно строится, появляется только в лабораторной работе 3.

Ключ атомарно резервируется через INSERT с ON CONFLICT (key) DO NOTHING, и это происходит до создания самой поездки. Внешний ключ idempotency_keys.trip_id к trips.id объявлен DEFERRABLE INITIALLY DEFERRED, поэтому можно вставить резервирующую строку с trip_id, которого в trips пока ещё нет: проверка внешнего ключа откладывается до COMMIT той же транзакции, а к этому моменту строка в trips уже вставлена.

Порядок операций важен. Если бы поездка создавалась раньше резервирования ключа, несколько параллельных запросов с одним ключом на одного водителя сначала столкнулись бы друг с другом на ограничении "один активный водитель у trips", а не корректно дедуплицировались бы по ключу. Это была реальная ошибка, которую поймал на тесте: 10 параллельных запросов с одним новым ключом сначала дали один 201 и девять 409 driver_busy вместо одного 201 и девяти 200. После того как поменял порядок операций (сначала резервирование ключа, потом создание поездки), тот же тест даёт один 201 и девять 200 с одним и тем же id у всех.

## Dockerfile (задание со звёздочкой)

Сборка многостадийная. Первая стадия на образе golang:1.27-alpine компилирует статический бинарь с CGO_ENABLED=0. Вторая стадия на образе gcr.io/distroless/static-debian12:nonroot содержит только этот бинарь, без shell и без toolchain. Процесс идёт от uid 65532, не от root, это дефолтное поведение выбранного базового образа.

Собрать образ:

```
docker build -f deploy/Dockerfile -t trip-service .
```

Размер итогового образа: 22.7 MB.

Запустить рядом с PostgreSQL в одной docker-сети (переменные такие же, как в .env.example, DATABASE_URL указывает на контейнер базы по его имени в сети):

```
docker run -d --network <сеть> -p 8080:8080 \
  -e HTTP_ADDR=:8080 -e LOG_LEVEL=info -e SHUTDOWN_TIMEOUT=10s \
  -e DATABASE_URL=postgres://tripgo:tripgo@<контейнер-бд>:5432/tripgo?sslmode=disable \
  -e DATABASE_MAX_CONNS=10 -e DATABASE_MIN_CONNS=2 \
  -e DATABASE_MAX_CONN_LIFETIME=30m -e DATABASE_CONNECT_TIMEOUT=5s -e DATABASE_QUERY_TIMEOUT=3s \
  trip-service
```

/ready отвечает 200, когда база доступна. docker stop отправляет SIGTERM, сервис укладывается в SHUTDOWN_TIMEOUT: пишет в лог "shutdown signal received", потом "trip-service stopped" и выходит сам, до принудительного SIGKILL дело не доходит
